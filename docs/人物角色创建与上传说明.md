# 人物角色创建与上传说明

这份说明帮助你写一个人物角色，并把它导入「多人格讨论工作台」。目前网页图鉴接受 **JSON 文件**：一个文件可以写一个人物，也可以写一个人物数组。首次使用建议先从下面的示例改起。

## 先确认要用在哪个模式

| 模式 | `modes` 中填写 | 网页图鉴导入后能否在讨论中选用 |
| --- | --- | --- |
| 娱乐 | `entertainment` | 可以 |
| 情感分析 | `emotion` | 可以 |
| 工作 · 创造项目 | `product` | 可以 |
| 辩论 | `rational` | 可以。入座时按顺序分到正方、反方或主持，点人物卡上的阵营按钮（如「正方 ⇄」）可以换 |

网页导入的人物只在**当前页面打开期间**有效；刷新页面后需要重新导入。想让所有用户长期看到，需要由项目维护者把文件加入 `frontend/personas/` 下对应模式的文件夹（`entertainment/`、`emotion/`、`product/`；辩论用 `rational/`，需要新建）并重新发布。

## 一个好用的人物需要写什么

先用自己的话回答以下问题，再填入 JSON。角色要有自己的视角和做法，避免只写“聪明、专业、乐于助人”一类笼统形容。

| 内容 | 想清楚的问题 | 对应字段 |
| --- | --- | --- |
| 名字和身份 | 他叫什么？在讨论中负责什么？ | `name`、`identity` |
| 擅长的内容 | 他熟悉什么领域？哪些事不该装懂？ | `knowledge`、`boundaries` |
| 思考方式 | 遇到问题先看什么、怎样判断？ | `thinking` |
| 看重的原则 | 当观点冲突时，他优先坚持什么？ | `values` |
| 可选性格 | 同一个人物可以用哪几种做事和说话方式？ | `personalities` |
| 外观 | 想让他在场景中是什么颜色？ | `visual.shirt`，可选 |

`identity`、`knowledge`、`thinking` 和 `values` 决定**这个人怎么看问题**；`personalities` 决定**这次用什么方式表达**。性格选项之间最好有明确区别，例如“先安抚再提建议”和“先指出关键矛盾”，而不只是换两个近义词。边界写可执行的规则，例如“没有依据时不把猜测说成事实”。

## 直接可用的 JSON 示例

把下面代码块中的内容复制到一个新文件，保存为 `user-xiaozhi-001.json`。修改名字和内容时，保留 JSON 的双引号、逗号及括号。这个示例用于**娱乐模式**；改为情感分析、工作或辩论模式时，把 `modes` 的值分别改成 `emotion`、`product` 或 `rational`，并相应改写人物设定。

```json
{
  "id": "user-xiaozhi-001",
  "name": "小知",
  "modes": ["entertainment"],
  "identity": "生活观察员，负责把抽象话题拉回日常例子",
  "knowledge": ["校园生活", "日常消费", "朋友间的沟通"],
  "thinking": "先找一个具体场景，再比较不同做法的实际效果；听到新信息时愿意修正判断",
  "values": "具体、诚实、尊重不同经历",
  "personalities": [
    {
      "id": "gentle",
      "label": "温和",
      "behavior": "先接住别人的观点，再补一个生活中的例子",
      "style": "短句、口语化，不急着下结论"
    },
    {
      "id": "witty",
      "label": "俏皮",
      "behavior": "用贴切的小比喻指出反差，笑点针对事情而不是人",
      "style": "轻松、简短，严肃话题不强行开玩笑"
    }
  ],
  "defaultPersonalityId": "gentle",
  "boundaries": [
    "不知道的事直接说不知道",
    "不编造真实人物的经历或言论"
  ],
  "visual": { "shirt": "#5F82B0" }
}
```

### 字段怎么填

| 字段 | 填写规则 |
| --- | --- |
| `id` | 人物的唯一标识。建议用小写英文字母、数字和短横线；不要与已有或本次导入的其他人物重复。以后用同一个 `id` 再导入，会替换当前页面中同 `id` 的人物；同一个文件里 `id` 重复的，只导入第一个。 |
| `name` | 页面上显示的名字，建议简短、容易辨认。 |
| `modes` | 一个或多个模式的英文标识：`entertainment`、`emotion`、`product`、`rational`。建议明确填写；省略时放进导入时图鉴所在的模式。 |
| `identity` | 一句话写清身份和职责，不要只写头衔。 |
| `knowledge` | 字符串列表，写熟悉的领域或经历；不要把没有把握的专业能力写进去。 |
| `thinking`、`values` | 分别写思考步骤和判断时重视的原则。 |
| `personalities` | 至少写一个性格选项；建议写两个以上。每项可写 `id`、页面显示的 `label`、做事方式 `behavior`、说话方式 `style`，以及可选的开场口头禅 `opener`。 |
| `defaultPersonalityId` | 填 `personalities` 中某一项的 `id`，作为默认选中的性格。 |
| `boundaries` | 字符串列表，写角色不该做的事、遇到信息不足时的处理办法。 |
| `visual` | 可选。`shirt` 是 `#RRGGBB` 格式的衣服颜色；省略时系统会分配默认配色和像素形象。要用图片头像，可填 `image` 为浏览器能够访问的图片地址。 |

**系统能加载的最低要求**是：顶层有非空的 `id`、`name`，并且 `personalities` 是至少包含一个性格对象的数组。上面的其余内容虽然不是简化格式的强制项，但直接影响人物能否表现出稳定、可区分的特点，建议填写完整。不要把 API Key、密码或真实人物的私密资料放进人物文件。

## 上传步骤

1. 将 JSON 内容保存为 UTF-8 编码的 `.json` 文件。文件里只放 JSON，不要复制示例的代码围栏；JSON 不能写注释，也不能在最后一项后多加逗号。上传按钮只接收 JSON，不能直接上传 Word、PDF 或本地头像图片。
2. 打开工作台，在右上角进入「图鉴」，切换到目标模式，点击「导入人物 JSON」（情感分析和工作模式的按钮文字略有不同），选择文件。
3. 查看导入结果。如果显示“未加载”，展开问题列表，按提示修改文件后重新导入；如果显示“已加载，有提醒”，人物仍可使用。
4. 回到「选择人物」，找到新人物并选择性格。开始讨论至少需要 **两个人物**，所以只导入一个新人物时，还要再选一位。

导入后若看不到人物，先确认 `modes` 与当前标签一致。完整格式没有头像时可能出现提醒，但不影响导入。如果刷新后人物消失，重新选择本地 JSON 文件导入即可。

## 想写更详细的人格资料包

四个模式也都支持「人格资料包协议 v1.0」，适合希望细分知识强项、弱项、价值优先级、性格选项、说话风格和边界的用户。可参考[完整示例](../persona-protocol/examples/aleng.persona.json)；其顶层结构为 `{ "schemaVersion": "1.0", "persona": { ... } }`。它与上面的简化格式是**两种不同格式**，不要把字段混在一起。

完整格式的 `persona` 必须包含 `id`、`name`、`description`、`version`、`modes`，以及 `identity`、`knowledge`、`worldview`、`personality`、`communicationStyle`、`boundaries`、`visual` 七组资料。`personality.traitOptions` 需有 2–8 项，`defaultTraits` 需从中选 2–4 项；`visual.color` 和 `visual.defaultLabel` 必填，头像可以不填。`modes` 可填 `entertainment`、`emotion`、`product`、`rational`；含 `rational` 时 `worldview.assumptions`、`judgmentFocus`、`blindSpots` 必填，`boundaries.factVsOpinion` 必须是 `always_label`。完整字段以[协议校验器](../persona-protocol/src/protocol.mjs)为准。

项目维护者可在仓库根目录运行 `node persona-protocol/src/cli.mjs 文件.json` 检查**单个人格资料包**。网页图鉴也会在导入时给出校验结果；这个命令不用于上面的简化格式，也不用于包含多个人物的数组文件。
